# MatMentor (Ronin) — Ralph Battle-Test PRD

## P0: Core Functionality — "Does It Work?"

- [ ] **Auth flow:** magic link signup via `/auth/login` -> email OTP -> `/auth/confirm` verifies token -> redirect to `/chat` -> session persists across page reloads -> `POST /auth/logout` clears session and redirects to login (If auth is broken, nothing else in the app is testable — this is always the first thing to verify)
- [ ] **Auth guard:** unauthenticated users hitting any `(app)/*` route get redirected to `/auth/login`; authenticated users hitting `/auth/login` get redirected to `/chat` (Guards protect every downstream feature — a gap here means data leaks to anonymous visitors)
- [ ] **Auto user creation:** first login creates a `users` row in DB via `(app)/+layout.server.ts` with `authId` and `email` from Supabase, then redirects to `/onboarding` because `onboardingCompleted` is false (The app auto-provisions profiles — if this breaks, new users see a 404 instead of onboarding)
- [ ] **Onboarding flow:** form at `/onboarding` collects belt, experience, frequency, goals, struggles -> submits form action -> updates user row -> sets `onboardingCompleted=true` -> redirects to `/chat` (Onboarding gates the entire app — if it doesn't set the flag, users loop forever)
- [ ] **Chat with Musashi:** `/chat` page loads, user types a message, `POST /api/chat` streams an AI response back via `toUIMessageStreamResponse()`, response renders in the chat UI (This is the core product — an AI coaching conversation. If streaming breaks, the app is dead)
- [ ] **Message persistence:** user message is saved to `messages` table before streaming; assistant response is saved in `onFinish` callback; both reference a `conversations` row (Without persistence, every page refresh loses the conversation — users think the app is broken)
- [ ] **Session logging:** `POST /api/sessions` accepts training session data (type, duration, RPE, energy, mood, positions, techniques) and inserts into `sessions` + `events` tables with correct foreign keys (Session logging feeds the AI's knowledge of the user — without it, Musashi has no data to coach from)
- [ ] **Weekly summary:** `POST /api/summary` aggregates last 7 days of sessions + events, calls Claude Haiku to generate a coaching summary, saves it as an assistant message in the conversation (Summaries are the "aha moment" — they prove the app is tracking progress and learning)
- [ ] **Summary cron:** `GET /api/summary/cron` iterates all onboarded users, generates summaries for those with sessions, requires `CRON_SECRET` bearer token (The cron job automates weekly summaries — without auth check, anyone can trigger expensive AI calls)
- [ ] **Rate limiting:** free users are capped at 20 messages/week, paid at 100; `messageCounts` table tracks per-user weekly counts; exceeding the limit returns 429 (Rate limiting prevents runaway API costs — if it's bypassed, one user can drain the AI budget)
- [ ] **Profile page:** `/profile` displays user data (belt, experience, goals, subscription tier) and shows upgrade button for free users (The profile is where users see their identity in the app and manage their subscription)
- [ ] **Navigation:** `BottomNav` component renders on all `(app)/*` pages with links to chat, game, progress, profile (Navigation is how users move between features — if it breaks, they're trapped on one page)

## P1: Error Handling — "What Happens When Things Go Wrong?"

- [ ] **Chat API auth failure:** `POST /api/chat` returns 401 when `safeGetUser()` returns null, and the UI handles it gracefully instead of showing a raw error (An expired session mid-chat is common — the user needs a clear "please log in again" message, not a crash)
- [ ] **Chat API user not found:** `POST /api/chat` returns 404 when auth succeeds but no user profile exists in DB — verify this is handled in the UI (This happens if the DB row was deleted or never created — the error should guide the user to re-onboard)
- [ ] **OpenRouter failure:** when `OPENROUTER_API_KEY` is invalid or OpenRouter is down, `streamText` throws — verify the error is caught and the UI shows a user-friendly message, not a 500 (External API failures are inevitable — the user needs to know it's temporary, not that the app is broken)
- [ ] **Stripe checkout failure:** `POST /api/stripe/checkout` handles case where Stripe API call fails (invalid key, network error) — returns a meaningful error, not a raw 500 (Payment errors are the most sensitive — a confusing error during checkout loses the sale and the user's trust)
- [ ] **Stripe webhook invalid signature:** `POST /api/stripe/webhook` returns 400 for missing or invalid `stripe-signature` header (Webhook signature verification prevents attackers from faking payment events — if it fails silently, fake upgrades become possible)
- [ ] **Session logging validation:** `POST /api/sessions` handles missing required fields (type, durationMinutes, intensityRpe, energy) — currently no Zod validation exists; add it (Without input validation, malformed requests can insert garbage data that breaks summaries and charts)
- [ ] **Onboarding validation:** the onboarding form action returns `fail(400)` when belt is missing — verify all required fields are validated and the UI shows error messages (If onboarding silently accepts incomplete data, the AI coach works with garbage profile info)
- [ ] **Summary with no sessions:** `POST /api/summary` returns `{ summary: null, message: 'No sessions this week' }` when no sessions exist — verify the UI handles this state (New users will hit this immediately — they need encouragement to log their first session, not an empty page)
- [ ] **Cron auth bypass:** `GET /api/summary/cron` with no `authorization` header or wrong secret returns 401, not a summary (Without this check, anyone who discovers the URL can trigger AI calls for all users — that's a cost and privacy disaster)

## P2: Security — "Can Someone Break In?"

- [ ] **No cross-user data access:** every DB query in `+server.ts` files filters by the authenticated user's ID — verify no endpoint returns data belonging to a different user (This is the #1 security bug in multi-tenant apps — one missing WHERE clause and user A sees user B's data)
- [ ] **Stripe webhook signature verification:** `POST /api/stripe/webhook` uses `stripe.webhooks.constructEvent()` with the raw body and secret — verify this blocks forged events (Without signature verification, anyone can POST fake `checkout.session.completed` events and get free upgrades)
- [ ] **No secrets in client bundle:** verify that `STRIPE_SECRET_KEY`, `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, and `CRON_SECRET` are never imported in client-side code (any `+page.svelte`, `+layout.svelte`, or non-server files) (Vite tree-shakes server code, but a wrong import path exposes secrets in the browser bundle — instant compromise)
- [ ] **Auth token not in URL params:** verify the magic link flow uses `token_hash` only in the confirm endpoint, and tokens are never logged, stored in localStorage, or exposed in client state (Token leakage in URLs can be captured by browser extensions, analytics tools, or shared screenshots)
- [ ] **SQL injection prevention:** all DB queries use Drizzle's query builder or parameterized values — verify no raw SQL with string interpolation exists (Drizzle prevents injection by default, but a single `sql\`...\`` with unsanitized user input bypasses that protection)
- [ ] **JSON.parse in onboarding:** `src/routes/onboarding/+page.server.ts:16-17` calls `JSON.parse()` on form data for goals and struggles — verify malformed JSON is caught and doesn't crash the server (Uncaught JSON.parse errors are a denial-of-service vector — one malformed request kills the handler)

## P3: Edge Cases — "Realistic Messy Scenarios"

- [ ] **Rapid message sending:** user sends 5 messages in quick succession to `/api/chat` — verify rate limiting increments correctly and no race condition causes count to be off (Real users don't wait politely between messages — rapid-fire actions expose timing bugs in the counter increment)
- [ ] **Rate limit boundary:** free user at exactly 19 messages sends message 20 (should succeed) then message 21 (should get 429) — verify the boundary is correct (Off-by-one errors in rate limiting either block paying users too early or give free users extra messages)
- [ ] **Empty chat message:** user sends a message with empty text parts or no parts at all to `/api/chat` — verify the system doesn't save an empty message or crash (Users can submit empty forms via browser dev tools — the API should reject gracefully)
- [ ] **Onboarding double-submit:** user clicks the onboarding submit button twice rapidly — verify no duplicate user updates or errors (Double-submits are extremely common on mobile — without protection, you get race conditions on the user row)
- [ ] **Session with zero techniques:** `POST /api/sessions` with empty `techniquesHit` and `techniquesAgainst` arrays — verify the session is still created without events (Not every training session has specific technique tracking — the API should handle this gracefully)
- [ ] **Session with invalid technique slug:** `POST /api/sessions` with a `techniquesHit` entry containing a non-existent `slug` — verify the event is skipped (not crashed) and the session is still saved (Users or future UI bugs might reference deleted techniques — silently skipping is correct behavior)
- [ ] **Week boundary for rate limiting:** verify `getWeekStart()` in `src/routes/api/chat/+server.ts` correctly resets on Monday UTC — test with dates around Sunday/Monday midnight (A wrong week boundary means rate limits either never reset or reset at the wrong time — users get locked out or get double messages)
- [ ] **Subscription downgrade via webhook:** `customer.subscription.deleted` webhook looks up user by customer email — verify this handles the case where no user exists with that email (Stripe webhooks fire for all events, including test accounts — a missing user shouldn't crash the handler)

## P4: Integration Points — "Do The Pieces Talk To Each Other?"

- [ ] **Stripe checkout -> webhook -> tier upgrade:** completing a Stripe checkout fires `checkout.session.completed` webhook -> updates `subscription_tier` to `paid` in the DB -> the user's rate limit increases from 20 to 100 on their next message (This is two systems talking — Stripe and your DB. If the webhook handler has a bug, Stripe thinks the user paid but your app doesn't know)
- [ ] **Onboarding -> chat context:** after completing onboarding with specific belt/goals/struggles, the chat system prompt includes those values — verify `buildSystemPrompt()` in `src/lib/server/ai/system-prompt.ts` receives the correct user data (If onboarding data doesn't flow into the AI prompt, Musashi coaches a blank profile — the personalization is lost)
- [ ] **Session logging -> summary pipeline:** log a session with techniques -> call `POST /api/summary` -> verify the summary text references the logged techniques and session data (This validates that data flows from logging through aggregation to AI generation — a break anywhere produces empty or wrong summaries)
- [ ] **Chat message -> DB -> page reload:** send a message, get a response, verify both are saved in `messages` table, then reload the page — do previous messages persist in the UI? Check if `+page.server.ts` or `+page.svelte` loads message history (If messages are saved but never loaded on page mount, the persistence is write-only and users see an empty chat every time)
- [ ] **Cron summary -> conversation:** `GET /api/summary/cron` saves the generated summary as an assistant message — verify it appears in the user's chat the next time they open it (If the cron writes to a different conversation or the chat page doesn't load system-generated messages, summaries disappear)
